# Запись редактора в зону 2150(8) тома 2348: механизм и опыты

Как записать редактор `*RED` СИПРОД-П (РЕДÀКТ + DRАКОН) в зону 2150(8)
тома 2348 **без** библиотеки компилятора Паскаля из зоны 2570(8) - и при
этом транслировать именно компилятором из 2570, - и почему прежний
способ дописывал туда всю библиотеку 2570. Документ фиксирует диагноз,
проверенные опыты (08.11.2026, эмулятор dispak, Монитор-80 3.7) и
принятое решение. Исполнительный сценарий - `../scripts/запись-2348.sh`
(двухфазная сборка).

## 1. Диагноз

Прежняя колода записи (`../scripts/запись-2348.sh` до 08.11.2026):

```
user 419900 зс5^
лен 40(2348-wr)^
ЕЕВ1А3
*name
*call yesmemory
*perso:402570          ← библиотека Паскаля во временный каталог задачи
*call *pascal
<../source/redakt.pas>
*call *pascal
<../source/drakon.pas>
*to perso:402150       ← пишет ВЕСЬ временный каталог
*end file
```

Карта `*PERSO:LUZZZZ` читает библиотеку **во временный каталог задачи**
(PERSO.md проекта pascal-re), компилятор добавляет в тот же каталог
скомпилированные модули, а карта `*TO PERSO:LUZZZZ` пишет **весь**
временный каталог обратно на том. Поэтому в зону 2150 попадали PASCOMPL
и все модули run-time: монитор печатал «ДЛИНА LIBRARY 0o126 ЗОН» (86
зон), каталог зоны 2150 начинался с `DRАКОN`, `RЕДÀКТ` и далее
повторял каталог библиотеки 2570 (`РRО203`, `ZАР203`, `Р/31`...,
`РАSСОМРL`).

Карта `*STAND` в колоде не стояла, значит компиляция шла штатным
системным компилятором 15.0 (без `*STAND` монитор игнорирует PASCOMPL из
временного каталога и берёт предсвязанный оверлей) - то есть загрузка
`*perso:402570` была для компиляции **не нужна вовсе** и служила только
источником засорения временного каталога.

## 2. Почему не подошли «вычитание» и отбор связки

Проверены оба штатных механизма очистки временного каталога, описанных в
инструкции Паскаль-Монитора (wiki besm6.github.io, `pascal-monitor.txt`,
раздел 2.1) и в описании библиотеки (`pascal-re/library.txt`).

### 2.1. LIBSUB («вычитание» библиотеки)

Документированное применение: `*CALL LIBSUB` + карта `LUZZZZ` вычитает
содержимое perso-библиотеки из временного каталога, после чего
`*TO PERSO` дописывает в личную библиотеку только новые модули.

Опыты (запись в свободную зону 0o5000, контроль каталога `besmtool view`):

| опыт | колода | результат |
|---|---|---|
| 1 | `*perso:402570`, `*stand`, ОДНА программа, `*call libsub 402570`, `*to perso` | «ДЛИНА LIВRАRУ 003 ЗОН», в каталоге только программа - **работает** |
| 2 | две программы подряд, затем libsub | в каталоге только **последняя** программа, первая потеряна |
| 3 | две программы (compil. 15.1 через `*stand`) **без** libsub | обе программы на месте (0o65 зон с библиотекой Паскаля) |
| 4 | `*perso:402150` (целевая библиотека, как в примере инструкции), затем 402570,cont, две программы, libsub | первая скомпилированная программа потеряна |
| 5 | загруженный из perso модуль, libsub, `*to perso` | каталог пуст - вычтено всё |

Вывод: в этой реализации LIBSUB в каталоге выживает только **последний**
скомпилированный модуль; написанные раньше (и загруженные из perso)
записи вычитаются вместе с библиотекой. Для двух модулей редактора
(РЕДÀКТ и DRАКОН) механизм в одном задании неприменим; годится схема
«одна программа - одно задание - своя зона» с последующим слиянием
тремя заданиями, но есть способ проще (п. 3).

### 2.2. Отбор связки картами `*table:liblist`

В инструкции Дубны и в примере `wiki/examples/liblist.b6`:

```
*table:liblist(pasmitxt)
*liblist:670440
*to perso:41
```

Опыты:

| опыт | колода | результат |
|---|---|---|
| `*table:liblist(DRAKON)` + `*liblist:402150` + `*to personal library:405000` | одно имя | новая библиотека из одного модуля - **работает** |
| `*table:liblist(REDAKT,DRAKON)` (запятая) | два имени | карта не разобрана, отбор не действует: записано всё (0o106 зон) |
| две карты `*table:liblist(...)` подряд | по одному имени | действует только последняя (таблица перезаписывается) |
| `*table:liblist(REDAKT DRAKON)` (пробел) | два имени | отбор с одним «именем из двух слов», совпадений нет: пустая библиотека (003 зоны) |
| таблица и повторная `*to perso` | - | таблица **персистентна**: действует на все последующие записи |

Отбор работает, но синтаксис списка из нескольких имён на одной карте
не подобран, а персистентность таблицы усложняет последующее слияние.

### 2.3. Очистка временного каталога приказом Y и картами *EXCLUDE

Проверены и «лобовые» способы очистки временного каталога задачи после
трансляций:

- приказ Y программы pashelp («раздел уборки стандартных имён»
  инструкции Паскаля; исходник - pashelp.pas проекта pascal-re,
  процедура Remove) удаляет из каталога только имена, начинающиеся
  с «P/» и «PAS», и имя TIME, печатая «УБРАНО N».  Модули 2570 с
  прочими именами (PRO203, ZAP203, ARFALIB, OBPROG, LIBSUB, PULT,
  PAIB...) остаются;
- карта `*EXCLUDE` (Монитор-80) вызывает постоянную программу LIBDELET:
  цепочка `*EXCLU -> VTM tlibdelet -> GLIB -> LOADCALL(LIBDELET)` в
  star%.masm проекта monitor80-re.  Активный тест LIBDELET (08.11.2026,
  колоды и журналы - в комплекте libdelet-test) показал:

  | опыт | результат |
  |---|---|
  | штатная система Дубны (том 2148) | LIBDELET загружается и выполняется, но работника EXCLUDE в дистрибутивном томе нет: «ОТСУТСТВУЕТ EXCLUDE», задание завершается |
  | работник подложен в личную библиотеку | механизм подтверждён: поиск работника идёт и по личной библиотеке, резидентные ссылки (*OUTPUT*, *INPUT*, PT6) резолвятся |
  | LIBDELET с тома 2348 (сборка МГУ) | под монитором Дубны не работает: другая таблица PT6 («ИСПОРЧЕНЫ ПОДПРОГРАММЫ») |

  Итог: `*EXCLUDE` - не средство правки каталога (она отвязывает модули
  от памяти задачи, каталог на диске не трогает), а в среде dispak
  (монитор Дубны) до удаления дело вообще не доходит.  На собственном
  мониторе тома 2348 (сборка МГУ) `*EXCLUDE` работоспособна из коробки -
  LIBDELET того тома самодостаточна, - но для задачи записи редактора
  это ничего не даёт: в среде разработки (dispak) очистить временный
  каталог `*EXCLUDE`-ом нельзя.

## 3. Принятое решение: двухфазная сборка (компилятор - из 2570)

Требование к сборке редактора: трансляция - именно компилятором PASCOMPL
из зоны 2570(8), не системным оверлеем 15.0.  Загрузить же библиотеку
2570 и вычистить её из временного каталога штатно нечем (пп. 2, 2.3).
Поэтому сборка разделена на задания так, что в каждый момент во
временном каталоге находится ровно одна программа:

- **фаза 1а** - задание с `*perso:402570` + `*stand` (PASCOMPL берётся
  из временного каталога), трансляция ../source/redakt.pas, затем `*call libsub`
  с картой 402570 вычитает библиотеку из каталога, `*to perso:405000`
  пишет черновик А - только РЕДÀКТ (наблюдалось 0o16 зон);
- **фаза 1б** - то же с ../source/drakon.pas, черновик Б - только DRАКОН (0o11);
  **по умолчанию не выполняется** (TOLKO_REDAKT=1 в
  `pascal/scripts/запись-2348.sh`): транслятор схем ДРАКОН встроен в редактор
  как режим `*DRK`, отдельный модуль на томе не нужен - в зону 2150
  попадает одна библиотека 0o16 (РЕДÀКТ); вернуть DRАКОН - пустой
  переменной TOLKO_REDAKT=;
- **фаза 2** - задание `*perso:405000` + `*perso:405100,cont` (слияние
  черновиков во временном каталоге) + `*to perso:402150`: каталог и
  размещение модулей строит сам монитор (0o24 зон).

LIBSUB оставляет в каталоге только последний скомпилированный модуль
(п. 2.1), поэтому программы собираются по одной, а слияние вынесено в
отдельное задание.  Черновые зоны (0o5000, 0o5100) и хвост прежней
записи за новой длиной стираются сценарием свободным паттерном: том
возвращается к виду «занято только 0o2150..0o2173».

Приёмка на копии тома (08.11.2026, исходники master 047dc25 со свежими
исправлениями редактора - сквозная нумерация страниц, форма ST,
маркеры ячеек):

* баннер обеих трансляций - «PASCAL COMPILER 15.1 (28.10.26)» (PASCOMPL
  из 2570); «15.0 (15.02.82)» в журналах нет (сценарий запрещает);
* «ДЛИНА LIBRARY»: черновик А 0o16, черновик Б 0o11, связка 0o24 зон;
* каталог зоны 0o2150: RЕДÀКТ (1426 слов загрузки) и DRАКОН (70 слов),
  РАSСОМРL и модулей «P/» нет;
* занятые зоны вне области записи (0o2150..0o2255 и черновые) не
  изменились;
* smoke-пуск с тома (`*perso:402150` + `*perso:402570,cont` +
  `*call redakt`) на ../demo/demo1-текст.txt - выдача побайтно равна
  `../redakt.out` (16 строк).

Для сравнения: однодечная запись системным компилятором 15.0 (без
`*perso:402570`) тоже пишет в зону ровно связку и годится там, где
требование «компилятор из 2570» не действует; та редакция сценария
осталась в истории (коммит 1c7d3eb).

Примечание об эталонах печати. По эталону оригинала red-fill
единственный лишний пробел при выравнивании ставится в предпоследний
промежуток (как записано в правиле от 07.11.2026), и текущий исходник
ему следует. Прежние эталоны demo (`../redakt.out`, `demo6-печать.txt`)
были сняты с модуля, собранного до этого исправления, и содержат пробел
в последнем промежутке - поэтому свежесобранный редактор расходится с
ними на один пробел (demo1, строка 8) и на пустую строку шапки страницы
в печати *DRK, оставаясь верным оригиналу СИПРОДа на всех 16 эталонах
red-*. Эталоны перегенерированы с тома по текущему исходнику
(`../redakt.out`, `../demo/demo5-печать.txt`, `../demo/demo6-печать.txt`,
`../схемы/печать-каталог.txt`).

## 4. Состояние тома

Было (том 2348 до работ): зона 0o2150 - библиотека связки 0o126 зон
(компилятор + run-time + редактор), данные до 0o2255.

Стало (на рабочей копии после прогона сценария; боевой том переписывается
тем же сценарием): зона 0o2150 - библиотека редактора 0o24 зон
(0o2150..0o2173: 2 зонных каталога, РЕДÀКТ, DRАКОН); хвост прежней записи
0o2174..0o2255 и черновые зоны (0o5000.., 0o5100..) стёрты свободным
паттерном (4 нулевых байта + сигнатура `80 c7 f1 05` в шапке зоны);
остальные зоны тома, включая библиотеку Паскаля 0o2570 и рабочие зоны
re-siprod (0o2000, 0o2100), не изменены.

## 4а. Потолок памяти пуска с тома (09.11.2026)

Пуск с тома (`*perso:402150` + `*perso:402570,cont` + `*call redakt`)
грузит программу с 0o3122 - на 0o2122 слова выше, чем компиляционный
путь (`*call *pascal` + `*execute`, программа с 0o1000: память под
монитором освобождена компилятором).  Над программой размещается
run-time, между ними - куча; при её исчерпании run-time печатает карту
памяти с «МАЛО ПАМЯТИ В 75377» (низ стека 0o75400) и задание молча
заканчивается - карта печатается и с `*no lo` (это не загрузчик).

Записи 0o16 зон хватало впритык: куча 3004 слова; модуль 0o17 зон
(рост от *nSTA/*nSTN/*nMCP, +647 слов) оставлял 2357 - не хватало.
Правая страница в хранении ужата до `prowh = packed array [65..128]
of char` (66*11 = 726 слов экономии, те же индексы 65..128), модуль
снова меньше прежнего на 262 слова, куча 3266 слов.  Любой новый рост
модуля на ~600 слов снова упрётся в потолок - держать в голове.
